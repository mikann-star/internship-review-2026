03

产品增长：从看清数据，到降低使用门槛

PRODUCT GROWTH

围绕累计使用人数与 WAU，将工作拆为数据度量、用户认知、入口权限和交互体验四个环节。

01 / 数据基础

让目标可追踪

问题：缺少统一指标口径，各 Agent 负责人需手动取数，季度进度难以持续跟踪。

我的工作：拆解指标体系，覆盖核心目标、详细数据、技术数据、用户互动与反馈明细五个维度；搭建并持续迭代交易 Agent 数据报表。

配套梳理 Q3 WAU 提升计划，按周统筹产品与运营动作的优先级和落地节奏。

02 / 用户认知

让用户知道如何用

问题：用户不了解产品能力、适用场景和提问方法，长篇说明手册的阅读门槛较高。

我的工作：面向实习生群、交易大群与交易全员输出分层推广文案；梳理 Agent 能力和典型问答，完成内容脱敏，搭建介绍网页。

已上线的介绍网页包含首页概览、功能介绍、使用帮助和更新日志，将“能力说明”转化为易理解的使用指引。

03 / 入口与权限

让用户便捷进入

问题：入口路径较深，且使用前需分别申请知识库与天网权限。

我的工作：按部门分批开放侧边栏入口；维护交易域内自动开通部门白名单；推进域外两次审批合并为一次，审批通过后同步配置两类权限。

通过常驻入口与权限流程优化，减少查找、申请和等待环节。

04 / 交互体验

让首次使用更顺畅

我的工作：参考主流产品，优化首页交互逻辑与使用体验，并结合侧边栏常驻入口降低用户再次访问的成本。

体验优化与推广共同推进；现有数据能够观察整体趋势，尚不足以区分单项改动的独立效果。

05

PMO 协同：让规则与实际执行对齐

OPERATING RHYTHM

产品 PMO 关注需求与资源节奏；业务 PMO 关注跨端变更的前置评估与发布协同。

产品 PMO / 日常管理

明确节点、资源归属与接入边界

工作模块具体工作管理目的
需求节点管理需求提报与倒计时、取消排期与顺延、Quota 消耗通知、需求复盘提醒。让需求方掌握关键节点、工作要求与资源使用情况。
Quota 归属整理配合组织调整，更新部门与业务模块映射，核对各部门 Quota 消耗归属。减少资源归属歧义，为核算与规划提供依据。
客服域接入支持梳理接入待办并推进逐项落实，明确需求管理范围与边界。回应小迭代占比高、外域配合消耗高、评审规则不清等问题。

Quota 指需求资源配额。此处体现机制与交付，效率收益仍需后续数据验证。

产品 PMO / 提需节奏调整

从双版本提需，调整为单版本提需

B 端、履约与体验的提需节奏与研发和协作域不一致，导致小优化响应滞后、需求中途插入和优先级反复调整。

调整前

  • 每 2 个版本提需 1 次
  • 与单版本研发排期脱节
  • 临时协调成本较高

调整后

  • 每 1 个版本提需 1 次
  • 与协作域及研发节奏对齐
  • 及时响应日常优化

同步考虑约束：提需频次提高后，未充分论证或占位需求可能增多；由产品 TL 审核并打回，必要时由 PMO 协调。

业务 PMO / 双端变更管理

把影响评估前移到项目立项

消费者与商家侧变更分散管理，跨端影响评估不足；负责人介入偏晚，公示时间分散，可能造成信息过载和反复变更。

  • 统一 SOP：协助梳理消费者与商家体验相关规则、政策及业务变更流程，推动双端前置协同。
  • 前置评审：从公告发布前移至项目立项，按重大及敏感程度匹配评审角色与放量方式。
  • 固定窗口：将变更归集至周三发布，减少分散通知。

已形成流程机制；落地后的通知负担、变更返工及用户体验改善，仍需补充跟踪验证。

06

成长与复盘：从推进需求，到关注项目结果

LEARNING & REFLECTION
三点收获

建立交易全链路视角

从对业务的初步了解，逐步理解招商、商家运营、营销活动与履约管理之间的联系。梳理 Agent 边界时，不只看功能名称，也结合业务运转逻辑，判断 Skill、子 Agent 与业务场景之间的归属。

围绕核心指标拆解工作

从逐项响应需求，转向“目标 → 路径 → 动作”的结构化拆解。在累计使用人数达标后，将工作重心进一步聚焦 WAU，从新增用户、持续使用和质量改善等路径安排优先级与推进节奏。

形成项目整体视角

从关注单个需求的开发、测试和上线，逐步转向梳理各方职责、依赖与阻塞点。例如，判断自动建品能力应归属哪个 Agent、答疑场景是否需要拆分，以及定时任务阅读率应作为独立需求还是通用配置。

执行与闭环

01 流程设计需要先验证可执行性

设计 BadCase 修复流程时，默认各子 Agent 负责人能够主动参与，但未充分考虑已有排期和工作优先级，实际推进与预期出现偏差，后续由技术侧统一分配人员并调整方案。

改进：先确认执行人、职责与排期，再通过小范围运行验证；把能够稳定复用的流程沉淀为 SOP。

02 交付之后，需要继续追踪效果

双端变更 SOP 完成后，缺少对落地效果和推进过程的系统复盘；推广后曾主动追踪新增用户，但尚未形成每项工作都复盘的稳定习惯。

改进：在启动时约定复盘节点，分别检查结果是否达标、过程有哪些可复用或需修正的方法。
判断与专业深度

03 披露问题与立即解决是两件事

曾因担心优先级不高或判断不准确，未及时在项目会上提出问题，过早替团队做了取舍，减少了共同判断的机会。

改进：及时同步事实、影响与不确定性，由团队判断优先级；不把信息披露等同于立即投入资源。

04 加深对 Agent 架构的理解

标准问标注时，部分路由判断仍需回查系统提示词与挂载 Skill；对 A2A 类 Agent 的能力范围、组成和调用逻辑理解还不够深入。

改进：加强与技术同学的沟通，结合典型问题梳理能力边界与调用链，减少依赖临时查阅的判断。
07

未来规划：先验证场景，再沉淀可复用能力

WHAT COMES NEXT

基于原有方向，建议按“基础治理 → 单场景验证 → 平台化复用”推进。以下为规划建议，具体排期与目标待协同确认。

阶段 01 / 基础治理

资源透明，风险前置

  • 完善实际可用 Quota 的报告与提醒，识别外域配合项占用。
  • 对“消耗不足但需求排不上期”的情况，解释排期、配额与依赖之间的差异。
  • 梳理上游依赖与变更通知机制，减少鉴权等变化对业务使用的影响。
  • 评估将日级 AI 评测升级为小时级抽检，兼顾发现时效、成本与误报。
建议验收依据
资源阻塞可解释；关键依赖明确负责人；问题发现与修复耗时可跟踪。
阶段 02 / 场景验证

从技术指标走向业务结果

  • 以项目管理场景试点业务评测集，明确成功标准和判定规范。
  • 采用 AI 自动评测与人工抽样校验，校准一致性与准确性。
  • 选择一个高价值业务工作流，验证从输入到结果回填的完整闭环。
  • 在关键节点保留人工决策，对异常情况及时告警。
建议验收依据
场景任务成功率、人工复核一致率，以及业务耗时或转化改善可测量。
阶段 03 / 能力复用

逐步建设工作流管理能力

  • 支持模板与自然语言创建，复杂任务由技术参与配置。
  • 统一管理执行、暂停、周期与触达人群，查看记录和结果。
  • 逐步补充步骤耗时、失败原因、超时通知等运行信息。
  • 将验证有效的工作流沉淀为模板，对稳定重复步骤使用代码或固定组件。
建议验收依据
工作流复用率、稳定性、运行成本，以及人工介入次数可持续跟踪。
候选试点 / 供给缺口识别与转化

将业务经验落成能够验证结果的工作流

监测需求和在售库存，识别款式、尺码等维度的供给缺口，匹配潜在供货商家，辅助生成邀约与补货建议，跟进出价、入仓与结果回填，最终验证缺货改善情况。

需求与库存监测→识别供给缺口→匹配潜力商家→人工确认邀约→跟进出价与入仓→回填与效果验证

建议先确认数据可得性、业务负责人、人工决策边界与成功指标，再决定自动化范围。工作流管理平台应建立在已验证场景与共性需求之上。

PMO / 需要进一步定位的问题

配额结余不等于可立即排期

原稿显示季度 Quota 总消耗约为配额的 83%。后续应结合统计进度、研发可用排期和跨域占用，解释剩余配额与实际可用资源之间的差异，避免仅根据消耗比例判断资源效率。

AI 产品 / 依赖管理的具体教训

把上游变化纳入主动监控

原稿记录 9 月 22 日鉴权相关变更后，70 多轮对话因权限不足无法正常进行。后续需要前置同步依赖变更、验证关键权限，并明确异常发生后的责任人与处理路径。

下一阶段的工作重点：在产品侧持续改善稳定使用与任务完成，在项目侧加强资源协调、风险披露和效果复盘，让每项迭代都能回到业务目标进行检验。
